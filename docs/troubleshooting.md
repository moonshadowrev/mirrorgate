# Troubleshooting

Start with these three steps. They solve most problems.

1. **Run the self check.**
   - With shell access: `php bin/mirrorgate check --network` (add `--env=/path/to/.env` if the file is not in the project root).
   - Without shell access: enable the admin endpoint temporarily and call `POST /__mirrorgate/check` ([deployment-shared-hosting.md](deployment-shared-hosting.md#self-check-without-shell-access)).
   - Every line is `OK`, `WARN` or `FAIL`. Fix all `FAIL`s first.
2. **Read the logs.** See [Reading the logs](#reading-the-logs).
3. **Use the request ID.** Every error page generated by MirrorGate shows a request ID, also sent as the `X-MirrorGate-Request-Id` response header. The same ID is in the log lines of that request.

## Reading the logs

MirrorGate never prints errors to visitors (`display_errors` is off from the first line of the front controller). Everything goes to log files.

### The bootstrap log

If the configuration cannot be loaded or the container cannot be built, no normal logger exists yet. MirrorGate then writes one JSON line per failure to:

```
<directory of the env file>/var/logs/bootstrap-<12 hex characters>.log
```

The 12 hex characters are a hash of the real path of the env file. The directory is created with a deny-all `.htaccess`. If it cannot be written, PHP's `error_log` is used instead (the web server's or PHP-FPM's error log).

Each line looks like:

```json
{"ts":"2026-11-10T04:27:48Z","rid":"3cc777f1882b8883","phase":"config","codes":["STORAGE_DIR:in_docroot"]}
```

`rid` is the request ID shown on the error page, `phase` is `config` or `container` (or, for runtime faults before the logger exists, a message such as `fatal_error`), and `codes` list the problems as `VARIABLE:reason`. Only codes are logged, never values. You can read the file with FTP or the panel's file manager (enable hidden files). The codes are explained in [configuration.md](configuration.md#validation-and-error-codes) and in [Boot failures](#boot-failures).

### The main log

After a successful boot, log lines go to `STORAGE_DIR/logs/mirrorgate-<12 hex>.log` (or `LOG_FILE`), as JSON, one event per line, rotated once to `.1` when larger than `LOG_MAX_BYTES`.

- The default level `warning` records problems only: upstream failures, rewrite failures, cache problems.
- Set `LOG_LEVEL=info` for the access log: `{"ts":...,"level":"info","msg":"access","rid":"...","ip_hash":"...","m":"GET","path":"/","st":200,"cache":"MISS","ms":25,"bytes":985,"up":"primary"}`. `st` is the status sent, `cache` is the cache result, `ms` the duration, `up` shows whether an upstream request was made (`primary`, `extra:<n>` or `-`).
- Set `LOG_LEVEL=debug` (or `APP_DEBUG=true`) for more detail while you debug. This does not change what visitors receive.
- Paths are shortened to the first segment by default (`LOG_PATH_MODE=segments`), and query strings are never logged. Use `LOG_PATH_MODE=full` temporarily if you need full paths.

If you cannot find the log, list `STORAGE_DIR/logs/`: the name has a suffix such as `mirrorgate-f4d50baf8a8c.log`.

## What the error pages mean

These are produced by MirrorGate itself. The language follows `ERROR_PAGE_LANG`.

| Status | Meaning | Usual cause |
|---|---|---|
| 400 | Bad request | Invalid request target (spaces, backslash, fragment, absolute URL), control characters in headers, duplicate or malformed `Host`, conflicting `Content-Length`/`Transfer-Encoding` |
| 403 | Access denied | Only from the web server rules for dotfiles (for example `/.env`); MirrorGate itself answers blocked paths with `404` |
| 404 | Not found | A path in `BLOCKED_PATHS` or `AUTH_PASSTHROUGH_BLOCK`; an admin request that failed authentication; or the origin's own `404` |
| 405 | Method not allowed | The method is not in `ALLOWED_METHODS`, or is `TRACE`/`CONNECT` |
| 413 | Request too large | Body above `MAX_REQUEST_BODY_BYTES` or `post_max_size`, or the web server's own limit |
| 414 | Address too long | URL above `MAX_URL_LENGTH` |
| 417 | Expectation failed | `Expect:` header other than `100-continue` (shown as a "bad request" page) |
| 421 | Misdirected request | The `Host` header is not `MIRROR_URL`'s host or an alias, or uses an unexpected port |
| 429 | Too many requests | Per-client rate or concurrency limit; the response has `Retry-After` |
| 431 | Header fields too large | Too many request headers, or a header line above `MAX_HEADER_BYTES` |
| 500 | Something went wrong | Configuration error, unexpected exception, `enable_post_data_reading` misconfigured, body spooling failure, or a PHP fatal error |
| 501 | Not supported | A WebSocket or other `Upgrade` request, an unknown method, or an unsupported `Transfer-Encoding` |
| 502 | Bad gateway | The origin could not be reached or answered wrongly: DNS, connect, TLS, reset, protocol error, an origin `502`, or an unsafe redirect |
| 503 | Temporarily unavailable | Circuit breaker open, account-wide concurrency cap, origin fetch budget exhausted, SSE stream slots exhausted, or an origin `503`. `Retry-After` is set |
| 504 | Gateway timeout | The origin did not answer within `ORIGIN_TIMEOUT` (or `ORIGIN_CONNECT_TIMEOUT`) |
| 508 | Loop detected | The request already passed through this instance (for example the origin proxies back to the mirror) |

`X-MirrorGate-Cache: ERROR` marks MirrorGate-generated error pages. 5xx errors are replaced by a stale cached copy when one is usable (see [caching.md](caching.md#stale-if-error)).

## Boot failures

A generic `500` page with a request ID on every URL, including `/`, means MirrorGate could not start. The bootstrap log has the reason.

| Code | Meaning and fix |
|---|---|
| `ENV_FILE:not_found` | No env file at the expected place. Check the lookup order in [configuration.md](configuration.md#where-the-configuration-comes-from), the `MIRRORGATE_ENV` constant of a stub, and the file name (`.env` is a dotfile: enable hidden files in your FTP client or file manager) |
| `ENV_FILE:not_readable` | The file exists but PHP cannot read it. Check the owner, group and mode (`0640` with PHP-FPM; `0644` with `mod_php` on hosts where PHP runs as a shared user), or whether the file is larger than 256 KiB |
| `ENV_FILE:in_docroot` | The env file is inside the document root. Move it above the docroot or use the `.env.php` form |
| `STORAGE_DIR:in_docroot` | `STORAGE_DIR` is inside the document root. Set it to a directory outside |
| `STORAGE_DIR:inside_public` | `STORAGE_DIR` is below the project's `public/` directory |
| `<VARIABLE>:<reason>` | A validation error, see [configuration.md](configuration.md#validation-and-error-codes). `bin/mirrorgate check` prints a message for each |
| `TRUSTED_PROXIES:file_unreadable` | A `@file:` entry has no path or the file cannot be read. Check the path (relative paths resolve against the env file directory) and its permissions |
| `CA_BUNDLE:not_found` | `CA_BUNDLE` does not point to an existing file |
| `BOOT:<ClassName>` | An unexpected exception during start-up. Check the PHP error log and that all extensions are loaded and the full release was uploaded (a missing `src/` file is a common cause) |
| `INI:enable_post_data_reading` | Only for form or multipart requests, see the next section |

Other boot-time checks:

- PHP version below 8.3 produces a PHP parse error (a blank page or a `500` from the web server), not a MirrorGate page. Check the PHP version for the domain.
- A blank white page and an empty log can mean PHP crashed before MirrorGate started (for example a disabled extension). Look at the web server and PHP-FPM error logs.

## Uploads and forms arrive empty

Symptom: file uploads or form posts reach the origin without data, or visitors get a `500` with the code `INI:enable_post_data_reading` in the main log.

Cause: with PHP's default `enable_post_data_reading=1`, PHP reads `multipart/form-data` and `application/x-www-form-urlencoded` bodies into `$_POST` and `$_FILES`, and `php://input` is empty. MirrorGate reads the raw body from `php://input`. If the setting is on and a form or multipart request arrives, MirrorGate answers `500` instead of forwarding an empty body.

Fix: set `enable_post_data_reading = 0` for the site.

| Handler | How |
|---|---|
| PHP-FPM, FastCGI, CGI, LiteSpeed | `.user.ini` in the document root (shipped in `public/` and in the project root). PHP caches `.user.ini` for `user_ini.cache_ttl` seconds (default 300). Wait five minutes or restart PHP |
| Apache `mod_php` | `php_value enable_post_data_reading 0` in `.htaccess` (shipped) |
| nginx | `fastcgi_param PHP_VALUE "enable_post_data_reading=0";` (in `examples/nginx.conf`) |
| PHP-FPM pool | `php_admin_value[enable_post_data_reading] = 0` in the pool file |

Confirm with the self check result `ini.enable_post_data_reading`. The value reported by `bin/mirrorgate check` on the command line comes from the CLI's own `php.ini` and can differ from the web value; the admin `POST /check` reports the web value.

Other body-related errors:

| Code or status | Meaning |
|---|---|
| `413` | The body is larger than `MAX_REQUEST_BODY_BYTES` or `post_max_size`, whichever is smaller. A declared length above the limit is refused before the body is read |
| `BODY:post_max_size` | PHP dropped part of the body because of `post_max_size` |
| `BODY:length_mismatch` (`500`) | The bytes received differ from the declared `Content-Length` and not because of `post_max_size`; for example a proxy altered the body |
| `BODY:temp_unavailable` (`500`) | PHP's temporary directory is not writable; large bodies (above 1 MiB) are spooled there |

## The origin is unreachable from the host

Symptom: `502` or `504` for everything not in the cache; `origin unreachable (dns)`, `(connect)` or `(tls)` in the check output.

Run `php bin/mirrorgate check --network` and see which step fails.

**DNS fails (`origin.dns`).**
- The host's resolver cannot resolve the origin name. Test from the host: `php -r 'var_dump(dns_get_record("overlord.team", DNS_A));'`.
- If the host has filtered or poisoned DNS, set `ORIGIN_RESOLVE_IP` to the origin's real address (look it up from another network). The primary origin host is then connected at that address without a DNS lookup.
- Remember the SSRF guard: a resolved address must be public. `origin resolves to a non-public address` means the name resolves to a private or reserved address (for example a captive portal or a filtered answer).

**Connect fails or times out (`origin.tcp`).**
- Outbound firewall. Many shared hosts only allow outbound connections to a short list of ports and sometimes only to local networks. Hosts in some countries filter connections to foreign networks or to specific services.
- Check `ORIGIN_PORTS_ALLOW` if the origin uses a port other than 80 and 443 (the port in `ORIGIN_URL` is added automatically).
- Raise `ORIGIN_CONNECT_TIMEOUT` (default 5) if the route is slow.

**Using a proxy.** If the hosting network blocks direct connections, route all upstream traffic through a proxy you control that can reach the origin:

```ini
OUTBOUND_PROXY=socks5h://user:password@proxy.example.net:1080
```

`socks5h://` makes the proxy resolve the origin name (use `socks5://` only if you must resolve locally). `http://` and `https://` proxies work too. The credentials are masked in all outputs. With a proxy configured, MirrorGate cannot validate the origin's address itself, so the SSRF guarantee moves to the proxy; only the host and port allow lists apply locally.

**IPv6.** MirrorGate prefers IPv4 and uses IPv6 only when the name has no `A` record. A host without working IPv6 and an origin with only `AAAA` records fails; use `ORIGIN_RESOLVE_IP` or a proxy.

**Iranian and similar hosting.** Some providers block outbound traffic to foreign hosts, or intercept TLS. If direct access fails, the options are `OUTBOUND_PROXY`, an `ORIGIN_RESOLVE_IP` fallback, or a different network location for the mirror (for example a VPS outside the filtered network). MirrorGate does not circumvent filtering by itself.

**The circuit breaker.** After `BREAKER_THRESHOLD` (5) transport failures within `BREAKER_WINDOW` (30 s), the breaker opens and requests are answered from the stale cache or with `503` and `Retry-After`, without contacting the origin, for `BREAKER_COOLDOWN` seconds (30, doubling up to `BREAKER_MAX_COOLDOWN`). One probe request then goes through. `GET /__mirrorgate/stats` (admin) shows the state. After fixing the cause the breaker closes by itself; there is no need to purge anything. The breaker state is stored in `STORAGE_DIR/breaker/`.

## TLS and certificate errors

- `origin unreachable (tls)`: the handshake with the origin failed. Common reasons are an outdated CA bundle on the host, a certificate that does not match the origin name, a protocol older than TLS 1.2, or TLS interception on the network.
- On hosts with an old trust store, download a current CA bundle (for example the Mozilla bundle published at curl.se/ca/cacert.pem) to a file outside the web root and set `CA_BUNDLE=/path/to/cacert.pem`. Verify its checksum against the publisher's. `bin/mirrorgate check` suggests this when it sees curl TLS errors 35, 51, 58, 60, 77 or 83.
- TLS verification cannot be switched off. If the origin uses a private CA, put that CA's certificate in a bundle file and use `CA_BUNDLE`.
- For your own mirror certificate: AutoSSL and Let's Encrypt need `/.well-known/` reachable on the mirror host (see [deployment-shared-hosting.md](deployment-shared-hosting.md#step-5-cpanel-https-with-autossl)).

## Redirect loops and wrong schemes

**"Too many redirects" in the browser.**
- The mirror sits behind a CDN with a "flexible" TLS mode (the CDN talks plain HTTP to your server) while your server redirects to HTTPS. Use full (strict) TLS between CDN and server, or stop redirecting at the server.
- `MIRROR_URL` uses a different scheme or host than the one visitors use. If visitors come through `https://www.ormantek.com/`, add `www.ormantek.com` to `MIRROR_ALIASES`. If `MIRROR_URL` says `http://` while the site is served over HTTPS, absolute links are rewritten to `http://` and browsers flag mixed content.
- The origin redirects `overlord.team` to `www.overlord.team` (or the reverse). `www.overlord.team` is not a mapped host, so the redirect target is a different, unmapped host and the visitor leaves the mirror. Set `ORIGIN_URL` to the canonical origin host (the one it redirects to) so that redirects stay inside the mapping.
- The origin redirects to HTTPS on the mirror host name because it received an unexpected `X-Forwarded-Proto`. MirrorGate sends `X-Forwarded-Proto`, `X-Forwarded-Host` and `X-Forwarded-Port` describing the **mirror**. Frameworks configured to trust them will generate mirror URLs; that is intended.

**Redirect to the origin host.** The `Location` host was not recognised: it is a host that is neither the origin host nor in `HOST_MAP`. `REDIRECT_EXTERNAL=block` turns such redirects into a `502` page.

**The `502` page appears for a redirect.** The origin sent a `Location` with a dangerous scheme, control characters or a backslash, or with `REDIRECT_EXTERNAL=block` pointed outside. The visitor sees the generic `502` page; compare the `Location` header the origin sends (`curl -i` against the origin itself).

## Links still point at the origin

1. Check the type: images, PDF and other binary types are never rewritten ([rewriting.md](rewriting.md#what-gets-rewritten)).
2. Is the host written in a form the origin or build tool generated at runtime? Compare with the list of supported forms in [rewriting.md](rewriting.md#forms-of-a-host-that-are-recognised).
3. Links inside JavaScript bundles: set `REWRITE_JS=true` (replaces host literals only), or avoid hard-coded hosts.
4. Links to sibling subdomains: add them to `HOST_MAP` and run the sibling instance ([multi-instance.md](multi-instance.md)).
5. Visible text: set `REWRITE_VISIBLE_TEXT=true` if hosts shown to people should change too.
6. The body was larger than `REWRITE_MAX_BYTES`, or did not fit into `memory_limit` (with `LOG_LEVEL=info` the log shows `rewrite_skipped` with a reason such as `too-large` or `memory`, and the cache header shows `BYPASS`). Raise `memory_limit` or `REWRITE_MAX_BYTES`.
7. RSC and Next.js navigation payloads are not rewritten unless `REWRITE_RSC=true` ([rewriting.md](rewriting.md#nextjs-and-similar-frameworks)).
8. An old cached copy? A changed configuration changes the cache fingerprint, so old copies are not served. If you edited something that is not part of the fingerprint, purge the path.
9. A service worker of the origin is serving old content from the browser's cache. Use `SERVICE_WORKER_MODE=block` once to clear it.

## Login, cookies and forms

- A login that works on the origin usually fails on a mirror, because sessions, CSRF tokens, OAuth redirect URIs and signed values are bound to the origin's host. This is expected. See [security.md](security.md#the-mirror-operator-sees-everything) before trying to make it work.
- Cookies disappear: they are `Secure` on an `https` mirror but the page is loaded over `http`, or `COOKIE_DOMAIN_MODE=drop` removed a `Domain` attribute that a sibling instance needed (use `rewrite`, see [multi-instance.md](multi-instance.md#cookies)).
- Cookies set by the origin are not shared with the browser's other subdomains of the mirror in `drop` mode; that is by design.
- "Invalid CSRF token" or "origin not allowed" errors on form posts: the origin compares the `Origin`/`Referer` of the request with its own host. MirrorGate maps these headers back to the origin host, but a site that checks additional values (for example a signed form field) will still refuse. Try `REWRITE_REQUEST_BODY=true` if a hidden form field contains the mirror URL.
- Forms posting to an absolute URL that is not rewritten (for example built in JavaScript) go straight to the origin.

## Blocked by the origin or its firewall

Symptom: the mirror returns `403`, a challenge page, or a Cloudflare error that works when you browse the origin directly.

- Origins and CDNs sometimes block hosting ranges, whole countries or unknown user agents. The mirror's server IP is what the origin sees. Ask the origin's operator to allow the address, or route through `OUTBOUND_PROXY` from an allowed network.
- Cache fills use a constant `User-Agent` (`Mozilla/5.0 (compatible; MirrorGate/<version>)`) and a constant `Accept: */*`, so every visitor shares one stored copy. Some firewalls reject unusual agents. To forward the visitor's own agent on cache fills, add it to the cache key: `CACHE_VARY_EXTRA=user-agent`. This creates one cache entry per distinct user agent and lowers the hit rate; consider `CACHE_RULES` and a smaller `CACHE_MAX_ENTRIES` if you do this.
- A WAF challenge page (JavaScript or CAPTCHA) cannot be solved by the mirror; the visitor sees the challenge, usually broken. If the origin's own CDN can be told to treat the mirror's IP as trusted, that is the clean fix.
- Rate limits at the origin: the mirror is one client from the origin's point of view. Lower `RATE_LIMIT_ORIGIN_FETCHES_PER_MINUTE` and rely on the cache.

## Streaming and SSE are buffered

Symptom: Server-Sent Events arrive in bursts or only when the connection closes.

1. Enable the admin endpoint temporarily and run:

   ```bash
   curl -N -H "Authorization: Bearer $TOKEN" https://ormantek.com/__mirrorgate/streamtest
   ```

   You should see five lines `chunk 1 t=0` to `chunk 5 t=2000` arrive about half a second apart. If they all arrive together, something between PHP and the browser buffers the output. If they are spaced out, the layers are fine and the problem is with the origin or the page.
2. Fix the buffering layer:

   | Layer | Fix |
   |---|---|
   | nginx | MirrorGate sends `X-Accel-Buffering: no`, which nginx honours. If you proxy through another nginx, set `fastcgi_buffering off;` (or `proxy_buffering off;`) for the site, and `gzip off;` |
   | Apache with `mod_proxy_fcgi` | Add `flushpackets=on` to the proxy worker: `<Proxy "fcgi://localhost/"> ProxySet flushpackets=on </Proxy>`. See `examples/apache-vhost.conf` |
   | Apache `mod_deflate` | `public/.htaccess` and the example vhost disable compression for requests that accept `text/event-stream`. If you use a different configuration, add `SetEnvIfNoCase Accept "text/event-stream" no-gzip=1 dont-vary=1` |
   | LiteSpeed | Disable "Enable Compression" for the virtual host if streams are held back. The LSAPI process time limit (about 30 seconds) also ends long requests |
   | CDN or host proxy | Disable response buffering for the path, or use a CDN plan that supports streaming. Some shared-hosting reverse proxies always buffer |
   | PHP | `output_buffering` and `zlib.output_compression` are switched off per streaming request when `ini_set` is allowed. If `ini_set` is disabled, set them in `php.ini` or `.user.ini` |

3. Duration. A stream ends after `SSE_MAX_DURATION` (60 s) and `EventSource` reconnects by itself. When `set_time_limit()` is disabled, or on LiteSpeed, the request is limited by `max_execution_time` (at most about 25 seconds on LiteSpeed); the self check reports this as `ini.runtime_ceiling`. Increase `max_execution_time` in the PHP settings if the host allows it.
4. Stream slots. Each open stream occupies a PHP worker for its whole life. The default `MAX_CONCURRENT_STREAMS=3` protects a small worker pool; visitors above the cap get `503`.
5. Gzip. MirrorGate does not compress streams. A layer in front that does will buffer them.

SSE on shared PHP hosting is best effort. For many long-lived connections, use a VPS ([deployment-vps.md](deployment-vps.md)) or move the stream to a dedicated host.

## Slowness, 429 and 503

- **Every page is slow on first visit, fast afterwards.** Normal for a cold cache. Slow origins make the first request slow; set `CACHE_RULES` for long TTLs on static paths, and check `X-MirrorGate-Cache` (`MISS` then `HIT`).
- **A burst of `429`.** Visitors behind one address (office, mobile carrier, or all visitors if the site is behind a CDN and `TRUSTED_PROXIES` is empty) share a limit. Raise `RATE_LIMIT_REQUESTS`, set `TRUSTED_PROXIES`, or add trusted addresses to `RATE_LIMIT_EXEMPT_IPS`.
- **`429` with `Retry-After: 1` for one visitor.** `RATE_LIMIT_MAX_CONCURRENT` (4 simultaneous requests per client) is reached; a page that loads many assets at once from a cold cache can hit it. Raise it a little if your PHP worker pool allows.
- **`503` with `Retry-After: 1`.** `GLOBAL_MAX_CONCURRENT` slots are all taken by requests waiting on the origin; the origin is slow or `GLOBAL_MAX_CONCURRENT` is too low for your traffic (but not above the number of PHP workers). Cache hits are not affected.
- **`503` with a longer `Retry-After`.** The circuit breaker is open, the origin fetch budget is used up (`RATE_LIMIT_ORIGIN_FETCHES_PER_MINUTE`), or the origin itself sent `503` (its `Retry-After` is used if it is at most 3600).
- **All PHP workers busy.** Lower `CACHE_COALESCE_WAIT_MS`, `MAX_CONCURRENT_STREAMS` and `GLOBAL_MAX_CONCURRENT`, or increase workers. Waiters and streams each hold a worker.
- **High CPU with big pages.** Rewriting scans the body. Lower `REWRITE_MAX_BYTES` or disable rewriting types you do not need (`REWRITE_JSON=false`, `REWRITE_XML=false`).

## Permissions and storage

- `storage.writable` fails: the PHP user cannot create `STORAGE_DIR`. Create the directory yourself and make it writable by the PHP user, or choose another location. With `open_basedir`, the directory must be inside it.
- Files created by MirrorGate are unreadable by the web server user (PHP and the web server run as different users on `mod_php` hosts): set `STORAGE_FILE_MODE=0644` and `STORAGE_DIR_MODE=0755`, understanding the isolation trade-off ([deployment-shared-hosting.md](deployment-shared-hosting.md#file-permissions)).
- `ratelimit.storage` fails: rate limiting is silently off because the state files cannot be opened or locked. Fix the permissions on `STORAGE_DIR/ratelimit` or use APCu.
- Disk or inode quota full: lower `CACHE_MAX_BYTES`, `CACHE_MAX_ENTRIES`, or purge (`php bin/mirrorgate purge --all`); add the garbage-collection cron job.
- `RATE_LIMIT_SALT` problems: the salt is generated in `STORAGE_DIR/run/salt`. If `STORAGE_DIR` is read-only, set `RATE_LIMIT_SALT` explicitly; otherwise a per-process fallback is used and limits and log hashes change on every request.
- Several instances sharing one `STORAGE_DIR` interfere with each other (breaker, salt, rate limits). Give each instance its own directory.
- NFS cache directory: set `CACHE_LOCK_MODE=mkdir`.

## Daemon problems

- Run `php bin/mirrorgate-daemon check --env=...` first. It validates the listeners, resolves the targets, and tests whether the bind addresses are free.
- `binding a non-loopback address requires DAEMON_ALLOW_PUBLIC_BIND=true`: expected; see [daemon.md](daemon.md#security-checklist).
- `target host is not in DAEMON_TARGET_ALLOWLIST`: the listener names a host that is not the origin host (or `EXTRA_ORIGINS`). Add it to `DAEMON_TARGET_ALLOWLIST` if that is intended.
- `cannot bind ... (98)` (address in use): another process, or an earlier daemon, uses the port. `status` shows whether a daemon runs.
- WebSocket clients get `403`: the `Origin` is not in `DAEMON_WS_ORIGIN_ALLOW` (default: your mirror hosts). Get `421`: the `Host` header is not a mirror host or the host of `WS_PUBLIC_URL`. Get `502`: the origin refused or mangled the upgrade; check the daemon log at `debug` level.
- Everything behind a reverse proxy shares one IP and hits `DAEMON_MAX_CONN_PER_IP`: add the proxy's address (for example `127.0.0.1`) to `TRUSTED_PROXIES` and make sure it sends `X-Forwarded-For`.
- The daemon exits with code 3: it restarted itself near `DAEMON_MEMORY_LIMIT`. Let the supervisor restart it, or raise the limit.
- Daemon stops after logout: you started it from a shell without `nohup`, `screen` or a supervisor.

## Verifying body handling

You can test request bodies against your own setup with `curl` and a mirror whose origin echoes requests (the repository's demo origin has an `/echo` route):

```bash
# Multipart upload
curl -s -F 'file=@/etc/hostname' https://ormantek.com/echo | head

# Form post
curl -s -d 'a=1&b=2' https://ormantek.com/echo | head

# Chunked upload
curl -s -H 'Transfer-Encoding: chunked' -d 'hello' https://ormantek.com/echo | head

# Oversize upload (expect 413)
head -c 20000000 /dev/zero | curl -s -o /dev/null -w '%{http_code}\n' --data-binary @- https://ormantek.com/echo
```

Each should reach the origin with the right body, or answer `413` for the last. Behaviour depends on the web server: Apache, nginx and LiteSpeed normally de-chunk request bodies before PHP, so MirrorGate re-sends the body with its own `Content-Length` and never uses `Transfer-Encoding: chunked` toward the origin. If `post_max_size` is smaller than `MAX_REQUEST_BODY_BYTES`, uploads between the two limits are rejected with `413` or `BODY:post_max_size`.

The repository's own scripts exercise these paths with PHP's built-in server (`bash scripts/e2e.sh` covers an oversize body with `413` and a `Content-Length` plus `Transfer-Encoding` conflict with `400`). Combinations with a specific web server stack are not part of the automated tests; verify them on your server before relying on them.

## Asking for help

Provide:

- Output of `php bin/mirrorgate version` and `php bin/mirrorgate check` (or the admin `/check` JSON). Both mask secrets.
- `php bin/mirrorgate config:dump` with secrets masked, if you need to share your configuration. Check that nothing sensitive remains before posting; origin and mirror hosts are included.
- The request ID of a failing request and the log lines with that ID (set `LOG_LEVEL=debug` temporarily).
- PHP version and handler (FPM, `mod_php`, LiteSpeed), the web server, and the layout you used.
- What `curl -i https://your-mirror/failing-path` returns.

Never post your `.env`, admin token, `STORAGE_DIR/run/salt`, or logs from a production site without removing sensitive data.
